# CI/CD Gates Setup: GitHub, GitLab & Other Providers

Every ruleset's **Integration** page in LiveReview (`/ci-rulesets/:id/integration`)
generates the copy-paste snippet and secrets/variables table for whichever
platform tab you pick — this page walks through the same setup, for reference.

## GitHub Actions

### 1. Add the workflow

On the ruleset's Integration page, select the **GitHub Actions** tab and copy
the generated workflow into your repo at `.github/workflows/livereview-gate.yml`.
The exact structure LiveReview generates looks like this (replace
`https://your-livereview-instance.com` with your own LiveReview URL):

```yaml
name: LiveReview Gate

on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  livereview-gate:
    runs-on: ubuntu-latest
    steps:
      - name: Evaluate LiveReview CI/CD ruleset
        env:
          LIVEREVIEW_API_KEY: ${{ secrets.LIVEREVIEW_API_KEY }}
          ORG_ID: ${{ secrets.LIVEREVIEW_ORG_ID }}
          RULESET_ID: ${{ secrets.LIVEREVIEW_RULESET_ID }}
          BASE_URL: https://your-livereview-instance.com
          PR_URL: ${{ github.event.pull_request.html_url }}
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
        run: |
          set -euo pipefail

          echo "Triggering LiveReview review for $PR_URL (commit $HEAD_SHA)"
          TRIGGER_RESP=$(curl -sf -H "X-API-Key: $LIVEREVIEW_API_KEY" -H "X-Org-Context: $ORG_ID" \
            -H "Content-Type: application/json" \
            -d "{\"url\":\"$PR_URL\"}" \
            "$BASE_URL/api/v1/connectors/trigger-review")
          REVIEW_ID=$(echo "$TRIGGER_RESP" | jq -r '.reviewId // empty')
          if [ -z "$REVIEW_ID" ]; then
            echo "Failed to trigger a LiveReview review: $TRIGGER_RESP"
            exit 1
          fi
          echo "Triggered review $REVIEW_ID"

          # Poll the SPECIFIC review we just triggered -- not a commit-SHA
          # lookup, which would silently reuse a different PR's already-
          # completed review of the same commit (e.g. a branch created
          # without new commits) instead of this PR's own review.
          # 90 attempts x 20s = 30 minutes, enough headroom for a large PR's diff.
          MAX_ATTEMPTS=90
          SLEEP_SECONDS=20
          echo "Waiting for review $REVIEW_ID to complete and evaluating the gate..."
          for attempt in $(seq 1 "$MAX_ATTEMPTS"); do
            RESP=$(curl -s -w '\n%{http_code}' -H "X-API-Key: $LIVEREVIEW_API_KEY" -H "X-Org-Context: $ORG_ID" \
              "$BASE_URL/api/v1/ci-rulesets/$RULESET_ID/evaluate?review_id=$REVIEW_ID")
            CODE=$(echo "$RESP" | tail -1)
            BODY=$(echo "$RESP" | sed '$d')

            case "$CODE" in
              200)
                echo "LiveReview: ALLOW"
                echo "$BODY"
                exit 0
                ;;
              422)
                echo "LiveReview: BLOCK -- a critical or security finding was found"
                echo "$BODY"
                exit 1
                ;;
              202)
                echo "  [$attempt/$MAX_ATTEMPTS] review $REVIEW_ID still running, retrying in ${SLEEP_SECONDS}s..."
                ;;
              401|403)
                echo "LiveReview: authentication failed (HTTP $CODE) -- check the LIVEREVIEW_API_KEY/LIVEREVIEW_ORG_ID secrets"
                echo "$BODY"
                exit 1
                ;;
              404)
                echo "LiveReview: ruleset or review not found (HTTP 404) -- check the LIVEREVIEW_RULESET_ID secret"
                echo "$BODY"
                exit 1
                ;;
              *)
                echo "  [$attempt/$MAX_ATTEMPTS] unexpected evaluate response ($CODE): $BODY"
                ;;
            esac
            sleep "$SLEEP_SECONDS"
          done

          echo "Timed out waiting for the LiveReview review to complete."
          exit 1
```

### 2. Add the secrets

Go to your repository → **Settings** → **Secrets and variables** → **Actions**
→ **Secrets** → **Repository secrets**, and add:

- `LIVEREVIEW_API_KEY`
- `LIVEREVIEW_ORG_ID`
- `LIVEREVIEW_RULESET_ID`

Add these as plain **Repository secrets**, not **Environment secrets** — an
environment secret can require manual approval or restrict which branches can
use it, which would block this gate from ever running.

### 3. Watch out for fork pull requests

If this repo accepts pull requests from forks: GitHub does not expose
repository secrets to workflow runs triggered by a fork's `pull_request`
event, by design. `LIVEREVIEW_API_KEY` will be empty for fork PRs unless you
switch the trigger to `pull_request_target` (review GitHub's security
guidance on that trigger first) or restrict this gate to same-repo PRs.

### 4. Block the merge button

A failing job on its own does **not** grey out the merge button. Go to
**Settings** → **Branches** → **Branch protection rules**, enable **"Require
status checks to pass before merging"**, and add the gate job's name (the
`jobs.<id>` key in the workflow YAML, e.g. `livereview-gate`, unless a `name:`
overrides it) to the required-checks list.

Verify the block took effect with:

```
gh pr view <n> --json mergeStateStatus
```

It reads `BLOCKED` once a required check is failing or still pending.

## GitLab CI

### 1. Add the pipeline job

On the ruleset's Integration page, select the **GitLab CI** tab and copy the
generated job into your project's `.gitlab-ci.yml`. The exact structure
LiveReview generates looks like this (replace
`https://your-livereview-instance.com` with your own LiveReview URL):

```yaml
livereview-gate:
  stage: test
  image: alpine:latest
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  before_script:
    - apk add --no-cache curl jq
  script:
    - |
      set -euo pipefail

      BASE_URL="https://your-livereview-instance.com"
      RULESET_ID="$LIVEREVIEW_RULESET_ID"
      ORG_ID="$LIVEREVIEW_ORG_ID"
      MR_URL="$CI_MERGE_REQUEST_PROJECT_URL/-/merge_requests/$CI_MERGE_REQUEST_IID"
      HEAD_SHA="$CI_COMMIT_SHA"

      echo "Triggering LiveReview review for $MR_URL (commit $HEAD_SHA)"
      TRIGGER_RESP=$(curl -sf -H "X-API-Key: $LIVEREVIEW_API_KEY" -H "X-Org-Context: $ORG_ID" \
        -H "Content-Type: application/json" \
        -d "{\"url\":\"$MR_URL\"}" \
        "$BASE_URL/api/v1/connectors/trigger-review")
      REVIEW_ID=$(echo "$TRIGGER_RESP" | jq -r '.reviewId // empty')
      if [ -z "$REVIEW_ID" ]; then
        echo "Failed to trigger a LiveReview review: $TRIGGER_RESP"
        exit 1
      fi
      echo "Triggered review $REVIEW_ID"

      # Poll the SPECIFIC review we just triggered -- not a commit-SHA
      # lookup, which would silently reuse a different MR's already-
      # completed review of the same commit instead of this MR's own review.
      # 90 attempts x 20s = 30 minutes, enough headroom for a large MR's diff.
      MAX_ATTEMPTS=90
      SLEEP_SECONDS=20

      for attempt in $(seq 1 "$MAX_ATTEMPTS"); do
        RESP=$(curl -s -w '\n%{http_code}' -H "X-API-Key: $LIVEREVIEW_API_KEY" -H "X-Org-Context: $ORG_ID" \
          "$BASE_URL/api/v1/ci-rulesets/$RULESET_ID/evaluate?review_id=$REVIEW_ID")
        CODE=$(echo "$RESP" | tail -1)
        BODY=$(echo "$RESP" | sed '$d')

        case "$CODE" in
          200)
            echo "LiveReview: ALLOW"
            echo "$BODY"
            exit 0
            ;;
          422)
            echo "LiveReview: BLOCK -- a critical or security finding was found"
            echo "$BODY"
            exit 1
            ;;
          202)
            echo "  [$attempt/$MAX_ATTEMPTS] review $REVIEW_ID still running, retrying in ${SLEEP_SECONDS}s..."
            ;;
          401|403)
            echo "LiveReview: authentication failed (HTTP $CODE) -- check the LIVEREVIEW_API_KEY/LIVEREVIEW_ORG_ID CI/CD variables"
            echo "$BODY"
            exit 1
            ;;
          404)
            echo "LiveReview: ruleset or review not found (HTTP 404) -- check the LIVEREVIEW_RULESET_ID CI/CD variable"
            echo "$BODY"
            exit 1
            ;;
          *)
            echo "  [$attempt/$MAX_ATTEMPTS] unexpected evaluate response ($CODE): $BODY"
            ;;
        esac
        sleep "$SLEEP_SECONDS"
      done

      echo "Timed out waiting for the LiveReview review to complete."
      exit 1
```

### 2. Add the CI/CD variables

Go to your project → **Settings** → **CI/CD** → **Variables**, and add:

- `LIVEREVIEW_API_KEY` — Visibility: **Masked** (or **Masked and hidden**).
- `LIVEREVIEW_ORG_ID` and `LIVEREVIEW_RULESET_ID` — Visibility: **Visible**.
  GitLab requires masked values to be at least 8 characters, and these are
  short numbers, so **Masked** will be rejected for them.

### 3. Don't protect the variables

Leave **"Protect variable" unchecked** on all three. A protected variable is
only exposed to pipelines running on a protected branch/tag, but this gate
needs to run on every merge request, including unprotected feature branches
— checking it will make the pipeline fail with `parameter not set` on any
non-protected branch.

### 4. Block the merge button

By default, GitLab lets you merge regardless of pipeline status — it only
shows the pipeline as a badge, and there's a real **"Merge immediately"**
button that bypasses a failing/running pipeline entirely. Go to
**Settings** → **Merge requests** → **Merge checks**, and enable
**"Pipelines must succeed"** to actually gate the merge button on
`livereview-gate`.

Via the API instead of the UI:

```
curl --request PUT --header "PRIVATE-TOKEN: <token>" \
  "https://gitlab.com/api/v4/projects/<id-or-url-encoded-path>" \
  --data "only_allow_merge_if_pipeline_succeeds=true"
```

## Any other CI/CD system (cURL / Bash)

Every ruleset also has a plain cURL/Bash snippet: it triggers a review, polls
the *exact* review it just triggered until it completes, and exits `0`
(allow) or `1` (block) based on the ruleset — the same trigger-then-poll
pattern as the GitHub and GitLab templates, just CI-agnostic.

### 1. Copy the snippet

On the ruleset's Integration page, select the **cURL / Bash** tab and copy
it. The exact structure LiveReview generates looks like this (replace
`https://your-livereview-instance.com`, `<YOUR_ORG_ID>`, and
`<YOUR_RULESET_ID>` with your own values):

```bash
#!/usr/bin/env bash
set -euo pipefail

# Every call needs both the API key AND the org context header --
# LiveReview requires X-Org-Context on every authenticated request,
# even for a single-org API key.
# LIVEREVIEW_API_KEY: create one under Settings > API Keys.
# PR_URL: set this to your pull/merge request's web URL.
# COMMIT_SHA: set this to the commit being tested (your CI's equivalent of $COMMIT_SHA).
BASE_URL=https://your-livereview-instance.com
ORG_ID=<YOUR_ORG_ID>
RULESET_ID=<YOUR_RULESET_ID>

echo "Triggering LiveReview review for $PR_URL (commit $COMMIT_SHA)"
TRIGGER_RESP=$(curl -sf -H "X-API-Key: $LIVEREVIEW_API_KEY" -H "X-Org-Context: $ORG_ID" \
  -H "Content-Type: application/json" \
  -d "{\"url\":\"$PR_URL\"}" \
  "$BASE_URL/api/v1/connectors/trigger-review")
REVIEW_ID=$(echo "$TRIGGER_RESP" | jq -r '.reviewId // empty')
if [ -z "$REVIEW_ID" ]; then
  echo "Failed to trigger a LiveReview review: $TRIGGER_RESP"
  exit 1
fi
echo "Triggered review $REVIEW_ID"

# Poll the SPECIFIC review we just triggered -- not a commit-SHA lookup,
# which would silently reuse a different PR's already-completed review
# of the same commit instead of this PR's own review.
# 90 attempts x 20s = 30 minutes, enough headroom for a large PR's diff.
MAX_ATTEMPTS=90
SLEEP_SECONDS=20
echo "Waiting for review $REVIEW_ID to complete and evaluating the gate..."
for attempt in $(seq 1 "$MAX_ATTEMPTS"); do
  RESP=$(curl -s -w '\n%{http_code}' -H "X-API-Key: $LIVEREVIEW_API_KEY" -H "X-Org-Context: $ORG_ID" \
    "$BASE_URL/api/v1/ci-rulesets/$RULESET_ID/evaluate?review_id=$REVIEW_ID")
  CODE=$(echo "$RESP" | tail -1)
  BODY=$(echo "$RESP" | sed '$d')

  case "$CODE" in
    200)
      echo "LiveReview: ALLOW"
      echo "$BODY"
      exit 0
      ;;
    422)
      echo "LiveReview: BLOCK -- a critical or security finding was found"
      echo "$BODY"
      exit 1
      ;;
    202)
      echo "  [$attempt/$MAX_ATTEMPTS] review $REVIEW_ID still running, retrying in ${SLEEP_SECONDS}s..."
      ;;
    401|403)
      echo "LiveReview: authentication failed (HTTP $CODE) -- check LIVEREVIEW_API_KEY/ORG_ID"
      echo "$BODY"
      exit 1
      ;;
    404)
      echo "LiveReview: ruleset or review not found (HTTP 404) -- check RULESET_ID"
      echo "$BODY"
      exit 1
      ;;
    *)
      echo "  [$attempt/$MAX_ATTEMPTS] unexpected evaluate response ($CODE): $BODY"
      ;;
  esac
  sleep "$SLEEP_SECONDS"
done

echo "Timed out waiting for the LiveReview review to complete."
exit 1
```

### 2. Set the environment variables

- `LIVEREVIEW_API_KEY` — set as a secret/credential in whatever your CI system uses.
- `PR_URL` — your pull/merge request's web URL.
- `COMMIT_SHA` — the commit being tested.

Both `PR_URL` and `COMMIT_SHA` need to be environment variables available to
the step that runs this script.

### 3. Requirements

`curl` and `jq` must be installed on the runner.

### 4. Check your platform's scoping rules

Check whether your CI restricts secrets/credentials by branch, environment,
or fork-originated pull requests (most do, in some form), and confirm your
platform has an equivalent "required check before merge" setting — a red CI
job on its own usually does not block merging without one.

### Using a different Git provider?

Bitbucket Pipelines, Azure Pipelines, Jenkins, CircleCI, etc. don't have a
ready-made native template yet — take the cURL/Bash snippet above and hand it
to a coding agent (Claude Code, GitHub Copilot, Cursor, etc.) with a prompt
like *"build me a `<your platform>` pipeline config that runs this bash
script as a gate, similar to how the GitHub Actions / GitLab CI version
works"* — it can translate the same trigger-then-poll logic into your
platform's native syntax.
