Risk-Based Auto-Approve: Verification Report

This page explains the auto-approve risk model. It shows the setup, the tests, the results, and the threshold settings. Every number on this page comes from a real, repeatable test. You can re-run each test yourself with the commands in the Setup tab.

The short answer to the most common questions

What is the risk threshold today?P20. The model approves only the safest 20% of an org's own recent reviews, and blocks the other 80%. A bigger number lets more through — see the row below and the Thresholds tab.
Is that threshold a fixed number?No. P20 is a setting an admin picks. The score that counts as "the safest 20%" is recalculated from the org's own recent reviews. Two orgs with the same P20 setting can have different cutoff scores. See the Thresholds tab.
What does a score of 0.42 mean?Scores run from 0 (looks safe) to 1 (looks risky). 0.42 is below the middle. A brand-new org with no history uses 0.5 as a placeholder cutoff. An org with real history almost never uses 0.5 — it uses its own calculated cutoff instead. See Quick Facts #4 below.
Does the model learn from mistakes?Yes. When a human reports that a merged PR caused a revert or an incident, the model takes one learning step the same day. A nightly job also re-fits the model from scratch and checks it did not get worse. See the Tests and Explain tabs.
Where do I change the settings?Settings → Auto Approve Policy, in the LiveReview app. Not on this page — this page only reports what the code does.

Fact #4, explained: why a clean PR can score 0.42

This needs its own fact because it caused confusion. Here is the full explanation in order.

Step 1

A score has no fixed meaning by itself. 0.42 only means something next to a cutoff.

Step 2

A brand-new org, with zero scored reviews, has no history to calculate a cutoff from. The code falls back to a placeholder cutoff of 0.5.

Step 3

0.42 is below 0.5. So even on day one, a docs-only edit is approved. It is close to the placeholder line, but it is on the approved side.

Step 4

Once an org has real review history, the placeholder 0.5 is never used again. The cutoff becomes "the score at the 20th percentile of my own recent reviews." The Thresholds tab shows this cutoff is usually different from 0.5, and is often much higher for a typical org.

What this means for you: 0.42 is not a sign that the model thinks a docs-only edit is risky. It is a sign that the placeholder cutoff (0.5) sits close to where ordinary, low-risk changes land. This is a known, reasonable property of the cold-start fallback, not a bug — but it is also why the placeholder cutoff should never be shown without this explanation next to it. This report no longer does that.

How the test data is written

Each test case is one block of plain data. It is not a database row. It is not a Go struct that only a programmer can read. It is a JSON file: internal/policyengine/testdata/scenarios.json.

{
  "name": "readme-only-edit",
  "rationale": "Docs-only change, no code risk at all.",
  "blast_hunks": [],
  "findings": [],
  "llm_class": { "class": "docs-only", "confidence": 9 },
  "diff": { "file_count": 1, "lines_added": 8 },
  "author_level": 2,
  "want": { "approve": true }
}

Anyone can read this file and understand the test case without running any code.

How a test case is run

The test code reads this file. For each case, it writes a real review row into a real test database, with the blast radius, the findings, and the LLM class from the JSON. Then it calls the real decision function, engine.RunWithPolicy. This is the same function the LiveReview app calls on a real pull request. The test does not re-implement the decision logic. It runs the real logic and checks the real answer against the want field in the JSON.

Why the database stays clean

Every row a test writes is deleted right after the test finishes. This happens even if the test fails or crashes. We checked this by running the whole test suite twice in a row and counting rows before and after. The count was zero both times, for every table.

Because of this, you can run these tests again and again, on any database, including a live one, and never need to clean up by hand.

Commands to run the tests yourself

Point DATABASE_URL at a test database, then run:

Keeping this page honest after the model changes

Every number on this page — every score, every weight, every approval rate — is embedded in the page as data, not typed in by hand. If you change the model's weights, the scenario corpus, or the reference mix the Thresholds tab compares against, this page will go stale unless you regenerate it. There is one command for that:

make regen-risk-report
# or directly:
python3 scripts/regen_risk_report.py

This script runs the same three tests listed above, reads the structured data they print (lines starting with SCDATA:, TDDATA:, TDSAME:, LCDATA:), and replaces this page's embedded data with exactly what the tests just computed. It refuses to run if any of the three tests fail, so this page can never embed a number from a broken test run. Run it, then check the diff — a page that changed more than you expected is itself useful information.

What this test work does not cover

  • No new features were added to the product. This work only tests and explains code that was already built.
  • "Force approve" (a human overriding a block) is a separate function, reached through a different code path. It is not covered by these 46 test cases.
  • These tests use made-up data with a known, clean pattern. They prove the mechanism is correct. They cannot prove the model will be accurate on messy, real-world data. Only real production use, tracked on the metrics dashboard, can show that.

Four groups of tests

Each group checks a different part of the system. Click a bucket chip below to see its test cases in the Results tab.

Group 1 — 46 example PRs (the scenario corpus)

What it is. 46 made-up pull requests, covering common and edge cases. Each one has a known correct answer: approve, or block, and why.
Why it matters. Without this, there is no way to know if the code behaves sensibly on everyday cases, not just on cases a developer happened to think of while writing the code.
What you do with it. If you change the model's weights or add a new rule, run this test. If a case that used to pass now fails, you know exactly which real-world situation you just broke.

Group 2 — math checks on the model itself

What it is. Small tests on the scoring formula, separate from any PR example. For instance: "if an admin sets a category's weight higher, does the score for that category actually go up?" and "does a brand-new org's model behave exactly like the hand-set starting point, with zero learning applied yet?"
Why it matters. These catch a broken formula even before it shows up as a wrong answer on a specific PR. A formula bug can be subtle; a one-line math check catches it directly.
What you do with it. If you ever touch internal/riskscore/model.go, these tests are your first line of defense. A failure here means "the formula itself is wrong," separate from "this one test case is wrong."

Group 3 — does learning actually change anything

What it is. Tests that feed made-up "this PR was reverted" or "this PR was confirmed safe" reports into the model, then check the model's weights really changed, in the direction those reports should push them.
Why it matters. A learning feature that silently does nothing is worse than no learning feature: it would give false confidence that the system is adapting, when it is not.
What you do with it. This is the proof that reporting a revert or an incident in the real app is not a dead button. See the Explain tab for the exact numbers.

Group 4 — the "preview" feature never has side effects

What it is. A test of the "Simulate" button in Settings — the one that shows "what would this policy have done to my last 20 reviews." It checks the preview never writes any real data.
Why it matters. If "Simulate" quietly wrote real decision logs while you were just trying out a setting, your real history would get polluted with fake trial runs.
What you do with it. You can trust the Simulate button to be read-only. Nothing you preview there can affect a real PR or a real training run.

The model in one sentence, before you read any numbers

Every review gets one number from 0 to 1, called the score. 0 means "looks safe." 1 means "looks risky." The score by itself tells you nothing — you always need to compare it to a cutoff. If the score is at or above the cutoff, the review is blocked. If it is below the cutoff, it is approved. The Percentile column below answers "where does this score sit, compared to a realistic set of other reviews" — see the Thresholds tab for exactly what that reference set is.

score = sigmoid( bias + sum of ( weight × category_multiplier × value ) for every signal )

There is no other step. No large language model makes this call — it is one weighted sum, squeezed into the 0-to-1 range by one standard function (sigmoid). Every signal's allowed range is listed in the Signal Reference table below, so you can judge for yourself what a normal value looks like.

That's 10 categories (security plus these 9), matching the Settings UI's Risk Model sub-tab exactly — the same list the auto-approve settings page stopped hiding under a collapsed "Other" section. A category dial of ×1.00 is not "this category is ignored" — it means "not weighted up or down relative to the others yet," and an admin can move any of these 10 dials independently at any time; the change takes effect on the very next score, with no retrain needed.

The compression note: files_changed and lines_added are passed through a squeezing step (log1p) before they reach the formula above. This is on purpose: without it, a diff with 10× more files would add exactly 10× more to the score, and a huge but otherwise harmless diff (like a generated file or a big rename) would dominate the result. After squeezing, going from 1 file to 10 files adds much less than going from 10 files to 100 — the signal still counts, but it cannot run away unbounded.

What the threshold setting actually does

The threshold is a percentile, written as P10, P20, and so on. P20 means: approve only the safest 20% of this org's recent reviews, and block the other 80%. A lower number is stricter (it approves less, blocks more). A higher number is more relaxed (it approves more, blocks less). Today's default is P20.

We built a test with 60 made-up reviews, shaped like a realistic repository's recent history: mostly small, clean changes, a smaller group of medium-risk changes, and a few clearly risky ones. We then checked what each percentile setting actually does to that mix.

Six settings, side by side, on the same 60 reviews

We included the two extreme edges, P0 and P100, on purpose — they are the settings that should be easiest to reason about, so they double as a check that the dial behaves the way anyone would expect.

SettingPlain meaningCutoff score% of reviews approved

The two edges, explained precisely:

  • P0 approves … of the … reviews, including the safest one in the set (a docs-only edit). The cutoff at P0 is the single lowest score in the whole mix, and nothing can score strictly below the lowest score in its own set — so at the strictest possible setting, everything is blocked, with no exceptions. This is proven by a passing test, not just described: go test ./internal/riskscore/... -run TestThresholdExperiment -v.
  • P100 approves … of … reviews — every one except the single riskiest review in the set. The cutoff at P100 is the single highest score in the mix, and that one review can never score strictly below its own value, so it alone stays blocked even at the most relaxed possible setting. "P100 allows everything" is almost true, but not quite: one review is still blocked, by definition, no matter how relaxed the setting is.

This is the actual, concrete reason the default is P20 and not something looser.

Is the threshold a fixed number? No — here is the proof

We ran the exact same setting, P20, against two different made-up histories: a "quiet" org whose recent reviews mostly scored low, and a "busy" org whose recent reviews mostly scored higher.

Same setting. Two different cutoff numbers. The setting (the percentile, like P20) stays fixed until an admin changes it. The number it turns into (the cutoff score) is recalculated from the org's own recent history, automatically, with no admin action needed. These are two different things, and this is the whole answer to "is the threshold static."

The system is a chain of checks, not one black-box decision

What it is. A pull request passes through four checks, in order: is the author senior enough, does it break a written rule (such as "no secrets in code"), does a risk score say it is safe, and does an AI reading of the diff agree it is safe. Any one check can block the PR.
Why it matters. If one part misbehaves, the other three still protect you. There is no single point where one bad number approves something dangerous.
What you do with it. When someone asks "how do we know this is safe," you can answer "no single step decides alone," and point at this report's Results tab for a specific example.

Two human safety nets, always available

What it is. A person with a high enough level can approve a blocked PR by hand, and must give a reason. A short delay can be set so a human has time to object right after an auto-approval, before it is treated as final.
Why it matters. The system never removes a person's ability to step in.
What you do with it. Watch how often "force approve" is used. If it happens a lot, the automatic settings are probably too strict, and that is a signal to review the Thresholds tab.

How the model updates itself

What it is. Two paths. First: the moment someone reports "this PR caused an incident," the model takes one small learning step, that same day. Second: once a night, a job re-builds the model from scratch using every report so far, and only replaces the live model if the new one is at least as good.
Why it matters. The first path means feedback matters immediately. The second path is a safety check: it stops a string of small, possibly-noisy daily updates from slowly making the model worse without anyone noticing.
What you do with it. Watch the "model confidence" indicator in Settings. It says how many real reports the model has learned from. Zero reports means the model is still running on hand-set starting values, not on your team's own history.

The formula

What it is. One formula, computed for every review:
z = bias + sum over every signal of (weight × category_multiplier × value)
score = sigmoid(z)        // squeezes z into the range 0 to 1
Why it matters. This is the entire model. There is no hidden step, no large language model making the final call. It is one weighted sum, run through one standard squeeze function.
What you do with it. To debug a surprising score, open the Results tab, click the row, and read the math table. It lists every signal, its value, its weight, its category multiplier, and what it added to z. The row with the biggest number is the reason for the score.
Where in the code: internal/riskscore/model.go (Score, Prior), internal/riskscore/features.go (the full signal list, called FeatureSpecs).

Three words this section needs, defined first

Outcome report. A short record of what happened to a PR after it was merged: it was later reverted, it caused an incident, or it was confirmed safe. This is the raw material the model learns from — in the real app, a person (or a webhook) creates one by clicking "mark as reverted" or similar.
Weight. One number inside the formula from the top of this tab. Each signal has its own weight. A bigger weight means that signal moves the score more. Learning, in this system, means "some weights change" — nothing else about the formula changes.
Held-out. Kept out of the training data on purpose. A held-out review is never shown to the model as an example to learn from — it is only used afterward, to ask "what do you think of this one now," so we can watch its score change honestly, step by step.

The learning loop, step by step

What it is. A test that starts a model at its hand-set defaults, then feeds it 40 made-up outcome reports. Every report in this batch follows one single, simple pattern: a report saying "this PR was later reverted" always has a high blast-radius value; a report saying "this PR was confirmed safe" always has a low blast-radius value. The test then checks what actually changed inside the model.

Why the score moved: the actual weight changes, not just the score. We printed every weight, before and after. The ones that moved the most are exactly the ones that measure blast radius, because blast radius was the one pattern in the training reports:

WeightBeforeAfterChange

Why did critical_count's weight drop so much? Because none of the 40 outcome reports in this test mentioned a critical finding — every single one of them only varied blast radius. A fresh model re-build only learns from the patterns actually present in its training reports. With no evidence either way about critical findings, the re-build pulls that weight most of the way back toward a low, cautious value, instead of keeping the full hand-set starting weight. In a real org, outcome reports would come from many different kinds of problems, not just one — this specific, large drop is a property of this test's narrow, single-pattern made-up data, not something to expect in production. It is a real and useful thing to know if you are ever reading a weight-change log and wondering why an untouched category moved.

Total movement for the held-out review: … → …, caused only by outcome reports, with no admin touching a weight by hand. That is the direct proof that reporting an incident in the real app is not a dead button.

A real limitation this work found

What it is. The finding-counting code only counts a finding if it has both a file path and a line number. A finding with neither is silently worth zero to every signal that counts findings.
Why it matters. In practice, every real finding has both. But if a future prompt or parser change ever produces a finding without them, that finding would vanish from the risk score with no error and no warning.
What you do with it. If a review's score looks lower than its finding list suggests, check whether every finding has a file path and a line number.
Where in the code: storage/reviews/taxonomy_report_store.go, buildWhereClause.

How we know this is correct, and what we still do not know

What it is. Three kinds of checks: 46 example PRs run through the real decision code, small math checks on the formula itself, and the learning-loop test above.
What this proves. The formula is implemented correctly, and the learning mechanism really does change the model, in the direction the data points to.
What this does not prove. Whether the model will be accurate on real, messy, production pull requests. All the data above is made up on purpose, with a clean, known pattern. Real accuracy can only be measured from the metrics dashboard, once real reports come in.
