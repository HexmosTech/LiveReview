Risk-Based Auto-Approve: Verification Report

This page explains the auto-approve risk model. It shows the setup, the tests, the results, and the threshold settings. Every number on this page comes from a real, repeatable test. You can re-run each test yourself with the commands in the Setup tab.

The short answer to the most common questions

What is the risk threshold today?P20. The model approves only the safest 20% of an org's own recent reviews, and blocks the other 80%. A bigger number lets more through — see the row below and the Thresholds tab.
Is that threshold a fixed number?No. P20 is a setting an admin picks. The score that counts as "the safest 20%" is recalculated from the org's own recent reviews. Two orgs with the same P20 setting can have different cutoff scores. See the Thresholds tab.
What does a score of 0.42 mean?Scores run from 0 (looks safe) to 1 (looks risky). 0.42 is below the middle. A brand-new org with no history uses 0.5 as a placeholder cutoff. An org with real history almost never uses 0.5 — it uses its own calculated cutoff instead. See Quick Facts #4 below.
Does the model learn from mistakes?Yes. When a human reports that a merged PR caused a revert or an incident, the model takes one learning step the same day. A nightly job also re-fits the model from scratch and checks it did not get worse. See the Tests and Explain tabs.
Where do I change the settings?Settings → Auto Approve Policy, in the LiveReview app. Not on this page — this page only reports what the code does.

Fact #4, explained: why a clean PR can score 0.42

This needs its own fact because it caused confusion. Here is the full explanation in order.

Step 1

A score has no fixed meaning by itself. 0.42 only means something next to a cutoff.

Step 2

A brand-new org, with zero scored reviews, has no history to calculate a cutoff from. The code falls back to a placeholder cutoff of 0.5.

Step 3

0.42 is below 0.5. So even on day one, a docs-only edit is approved. It is close to the placeholder line, but it is on the approved side.

Step 4

Once an org has real review history, the placeholder 0.5 is never used again. The cutoff becomes "the score at the 20th percentile of my own recent reviews." The Thresholds tab shows this cutoff is usually different from 0.5, and is often much higher for a typical org.

What this means for you: 0.42 is not a sign that the model thinks a docs-only edit is risky. It is a sign that the placeholder cutoff (0.5) sits close to where ordinary, low-risk changes land. This is a known, reasonable property of the cold-start fallback, not a bug — but it is also why the placeholder cutoff should never be shown without this explanation next to it. This report no longer does that.

How the test data is written

Each test case is one block of plain data. It is not a database row. It is not a Go struct that only a programmer can read. It is a JSON file: internal/policyengine/testdata/scenarios.json.

{
  "name": "readme-only-edit",
  "rationale": "Docs-only change, no code risk at all.",
  "blast_hunks": [],
  "findings": [],
  "llm_class": { "class": "docs-only", "confidence": 9 },
  "diff": { "file_count": 1, "lines_added": 8 },
  "author_level": 2,
  "want": { "approve": true }
}

Anyone can read this file and understand the test case without running any code.

How a test case is run

The test code reads this file. For each case, it writes a real review row into a real test database, with the blast radius, the findings, and the LLM class from the JSON. Then it calls the real decision function, engine.RunWithPolicy. This is the same function the LiveReview app calls on a real pull request. The test does not re-implement the decision logic. It runs the real logic and checks the real answer against the want field in the JSON.

Why the database stays clean

Every row a test writes is deleted right after the test finishes. This happens even if the test fails or crashes. We checked this by running the whole test suite twice in a row and counting rows before and after. The count was zero both times, for every table.

What this test work does not cover

  • No new features were added to the product. This work only tests and explains code that was already built.
  • "Force approve" (a human overriding a block) is a separate function, reached through a different code path. It is not covered by these 46 test cases.
  • These tests use made-up data with a known, clean pattern. They prove the mechanism is correct. They cannot prove the model will be accurate on messy, real-world data. Only real production use, tracked on the metrics dashboard, can show that.

What it is. Tests that feed made-up "this PR was reverted" or "this PR was confirmed safe" reports into the model, then check the model's weights really changed, in the direction those reports should push them.
Why it matters. A learning feature that silently does nothing is worse than no learning feature: it would give false confidence that the system is adapting, when it is not.
What you do with it. This is the proof that reporting a revert or an incident in the real app is not a dead button. See the Explain tab for the exact numbers.

Why it matters. If "Simulate" quietly wrote real decision logs while you were just trying out a setting, your real history would get polluted with fake trial runs.
What you do with it. You can trust the Simulate button to be read-only. Nothing you preview there can affect a real PR or a real training run.

The model in one sentence, before you read any numbers

Every review gets one number from 0 to 1, called the score. 0 means "looks safe." 1 means "looks risky." The score by itself tells you nothing — you always need to compare it to a cutoff. If the score is at or above the cutoff, the review is blocked. If it is below the cutoff, it is approved. The Percentile column below answers "where does this score sit, compared to a realistic set of other reviews" — see the Thresholds tab for exactly what that reference set is.

score = sigmoid( bias + sum of ( weight × category_multiplier × value ) for every signal )

There is no other step. No large language model makes this call — it is one weighted sum, squeezed into the 0-to-1 range by one standard function (sigmoid). Every signal's allowed range is listed in the Signal Reference table below, so you can judge for yourself what a normal value looks like.

The compression note: files_changed and lines_added are passed through a squeezing step (log1p) before they reach the formula above. This is on purpose: without it, a diff with 10× more files would add exactly 10× more to the score, and a huge but otherwise harmless diff (like a generated file or a big rename) would dominate the result. After squeezing, going from 1 file to 10 files adds much less than going from 10 files to 100 — the signal still counts, but it cannot run away unbounded.

What the threshold setting actually does

The threshold is a percentile, written as P10, P20, and so on. P20 means: approve only the safest 20% of this org's recent reviews, and block the other 80%. A lower number is stricter (it approves less, blocks more). A higher number is more relaxed (it approves more, blocks less). Today's default is P20.

We built a test with 60 made-up reviews, shaped like a realistic repository's recent history: mostly small, clean changes, a smaller group of medium-risk changes, and a few clearly risky ones. We then checked what each percentile setting actually does to that mix.

Six settings, side by side, on the same 60 reviews

We included the two extreme edges, P0 and P100, on purpose — they are the settings that should be easiest to reason about, so they double as a check that the dial behaves the way anyone would expect.

SettingPlain meaningCutoff score% of reviews approved

The two edges, explained precisely:

  • P0 approves … of the … reviews, including the safest one in the set (a docs-only edit). The cutoff at P0 is the single lowest score in the whole mix, and nothing can score strictly below the lowest score in its own set — so at the strictest possible setting, everything is blocked, with no exceptions. This is proven by a passing test, not just described: go test ./internal/riskscore/... -run TestThresholdExperiment -v.
  • P100 approves … of … reviews — every one except the single riskiest review in the set. The cutoff at P100 is the single highest score in the mix, and that one review can never score strictly below its own value, so it alone stays blocked even at the most relaxed possible setting. "P100 allows everything" is almost true, but not quite: one review is still blocked, by definition, no matter how relaxed the setting is.

Same setting. Two different cutoff numbers. The setting (the percentile, like P20) stays fixed until an admin changes it. The number it turns into (the cutoff score) is recalculated from the org's own recent history, automatically, with no admin action needed. These are two different things, and this is the whole answer to "is the threshold static."

The system is a chain of checks, not one black-box decision

What it is. A pull request passes through four checks, in order: is the author senior enough, does it break a written rule (such as "no secrets in code"), does a risk score say it is safe, and does an AI reading of the diff agree it is safe. Any one check can block the PR.
Why it matters. If one part misbehaves, the other three still protect you. There is no single point where one bad number approves something dangerous.
What you do with it. When someone asks "how do we know this is safe," you can answer "no single step decides alone," and point at this report's Results tab for a specific example.

Two human safety nets, always available

What it is. A person with a high enough level can approve a blocked PR by hand, and must give a reason. A short delay can be set so a human has time to object right after an auto-approval, before it is treated as final.
Why it matters. The system never removes a person's ability to step in.
What you do with it. Watch how often "force approve" is used. If it happens a lot, the automatic settings are probably too strict, and that is a signal to review the Thresholds tab.

How the model updates itself

What it is. Two paths. First: the moment someone reports "this PR caused an incident," the model takes one small learning step, that same day. Second: once a night, a job re-builds the model from scratch using every report so far, and only replaces the live model if the new one is at least as good.
Why it matters. The first path means feedback matters immediately. The second path is a safety check: it stops a string of small, possibly-noisy daily updates from slowly making the model worse without anyone noticing.
What you do with it. Watch the "model confidence" indicator in Settings. It says how many real reports the model has learned from. Zero reports means the model is still running on hand-set starting values, not on your team's own history.

The formula

What it is. One formula, computed for every review:
z = bias + sum over every signal of (weight × category_multiplier × value)
score = sigmoid(z)        // squeezes z into the range 0 to 1
Why it matters. This is the entire model. There is no hidden step, no large language model making the final call. It is one weighted sum, run through one standard squeeze function.
What you do with it. To debug a surprising score, open the Results tab, click the row, and read the math table. It lists every signal, its value, its weight, its category multiplier, and what it added to z. The row with the biggest number is the reason for the score.
Where in the code: internal/riskscore/model.go (Score, Prior), internal/riskscore/features.go (the full signal list, called FeatureSpecs).

Three words this section needs, defined first

Outcome report. A short record of what happened to a PR after it was merged: it was later reverted, it caused an incident, or it was confirmed safe. This is the raw material the model learns from — in the real app, a person (or a webhook) creates one by clicking "mark as reverted" or similar.
Weight. One number inside the formula from the top of this tab. Each signal has its own weight. A bigger weight means that signal moves the score more. Learning, in this system, means "some weights change" — nothing else about the formula changes.
Held-out. Kept out of the training data on purpose. A held-out review is never shown to the model as an example to learn from — it is only used afterward, to ask "what do you think of this one now," so we can watch its score change honestly, step by step.

A real limitation this work found

What it is. The finding-counting code only counts a finding if it has both a file path and a line number. A finding with neither is silently worth zero to every signal that counts findings.
Why it matters. In practice, every real finding has both. But if a future prompt or parser change ever produces a finding without them, that finding would vanish from the risk score with no error and no warning.
What you do with it. If a review's score looks lower than its finding list suggests, check whether every finding has a file path and a line number.
Where in the code: storage/reviews/taxonomy_report_store.go, buildWhereClause.

The Robot Checks First

A Risk-Based Auto-Approve Policy for Code Review

Summary

LiveReview can now auto-approve a pull request it has measured to be low-risk. This is not a shortcut. The robot runs a real check — several checks, in fact — before it decides anything. A human still reviews every change that the robot's checks flag as uncertain or risky.

The design is not a guess. It follows Meta's published RADAR system, a layered approach to exactly this problem at much larger scale. LiveReview already shared three of RADAR's five architectural pieces before this project started; we built the remaining two.

The result has been tested, not just built. Forty-six hand-written scenarios exercise every decision path the system can take. A live dashboard now shows, for each customer org, how many pull requests were approved, how many were blocked, how often a human overrode the robot, and how often an approval turned out to be wrong. Reviewer attention shifts from "every pull request" to "the pull requests that actually carry risk" — and we can show our work.

Working Backwards

Headline

LiveReview Ships Risk-Based Auto-Approval, Returning Reviewer Hours Without Lowering the Bar on Risky Changes

The customer problem

A team merging a hundred pull requests a week gives each one the same scrutiny. A one-line fix to a README gets read as carefully as a change to a billing calculation. That isn't rigor. It's an even coat of attention spread across a distribution that is anything but even — a small number of changes carry almost all of the actual risk, and the rest carry almost none.

Reviewer attention is the scarcest resource in this loop. It does not scale the way compute does. Ask a person to carefully read a hundred boring diffs a week, and eventually they stop reading carefully. That is not laziness. It is what happens to any human asked to apply full attention to a task that rarely rewards it.

Today, most teams have no lever for this problem beyond "review everything" or "review nothing." There is no middle setting that says: trust the obviously safe changes, and keep full scrutiny on everything else.

The solution

LiveReview's auto-approve policy is that middle setting. A pull request now passes through a layered funnel of checks — eligibility, static rules, a trained risk score, and an independent LLM classification — before the system decides whether a human needs to look at it before merge, or whether the robot's own checks are enough for now.

Every check still runs. Nothing about auto-approve means less checking — it means a different checker. Each stage writes down its own verdict, so "why was this approved" is always an answerable question, never a shrug. Any single stage can block the change outright, no matter what the other stages concluded.

The threshold for "safe enough" is a dial, calibrated against each customer's own recent history, not one fixed number forced on every team regardless of their risk profile. Turning the feature on costs nothing permanent: an org can set always_approve or never_approve on a specific repository, and a human can force an override on any single decision, in either direction, at any time.

Customer quote

"We stopped spending review time on changes that were never going to be rejected, and started actually noticing which ones deserved a second look," said an engineering lead at a mid-sized SaaS company piloting the feature.

Call to action

An org owner sets a starting percentile under Settings → Auto Approve Policy, watches the new Reports → Auto Approve dashboard for a week, and adjusts the dial using their own measured override rate and false-approve rate — not a guess, and not somebody else's benchmark.

Why Now

Pull request volume per engineer has grown faster than the careful, structured review process it gets pushed through. That process was built for a slower rate of change, and it has not been redesigned to match the new one — it has just been asked to go faster, which quietly means going shallower.

The risk in a typical week's changes is not evenly spread. A small fraction of pull requests carry nearly all of the blast radius — the reach of a change through the rest of the codebase — while the majority carry almost none. Equal scrutiny on every change means most reviewer time is spent on changes that were never going to fail.

Every customer running LiveReview today is already paying this cost in reviewer hours, whether or not anyone has measured it. Until now, there was no way to measure it, which made it easy to ignore and impossible to improve on purpose.

This is a mechanism change, not a headcount change. The lever here is how review attention gets allocated, not how many reviewers exist on a team. It pays off immediately, without a single new hire.

Why We Believe This Works: The RADAR Precedent

We did not invent this pattern from scratch. The design follows Meta's published RADAR system (arxiv 2605.30208): a layered funnel — eligibility, deterministic gates, a trained risk score, LLM semantic classification, and a final decision — rather than one opaque model making the entire call alone.

The decision funnel. Any stage can send a change to human review; only agreement across all of them reaches auto-approval.

Three lessons from that published system were carried over deliberately, because they came from a system already proven at a scale ours has not reached yet. First, a risk threshold must be a per-org dial, never one fixed cutoff applied everywhere — RADAR's own experiment comparing a strict and a lenient setting showed exactly why a single global number does not hold up across different teams. Second, safety outcomes — a revert, an incident, a confirmed-safe merge — must feed back into the model's calibration, or the system never learns from the very thing it exists to prevent. Third, the system must stay legible. Every decision shows its reasoning, stage by stage, never only a verdict with no explanation attached.

We also did not start from a blank page. Three of RADAR's five architectural ingredients already existed inside LiveReview in a different form before this project began: static rule gates (reused from the existing CI/CD gate system), per-finding severity and confidence scores (already produced by LiveReview's review engine), and blast-radius scoring (already computed per code change). The two genuinely new pieces were eligibility — deciding who can be considered for auto-approval at all — and the trained risk score itself.

What this buys the customer is simple: the architectural risk of "will this kind of system work at all" has already been retired by someone else's production deployment. What's actually new, and what actually needed building, is the integration into LiveReview's own review pipeline and its own ten-category finding taxonomy.

How the Robot Decides

Eligibility and static rules run first, and they are built to be simple on purpose. A rule that can be explained in one sentence is a rule that can be audited in one sentence. Either stage can block a change outright, no matter what a trained model further down the funnel would have concluded.

The risk score itself is a logistic regression — one of the oldest, most explainable models available — scoring blast radius and ten categories of finding severity into a single number between zero and one. A simpler, explainable model was chosen deliberately over a more powerful but opaque one, because this number decides whether a human ever looks at the code. In plain terms, the model works like this:

z     = bias + sum over every signal of (its value x its weight x its category importance)
score = squash(z) into a number between 0 and 1, where higher means riskier

The LLM classification check runs beside the risk score, not behind it. Either one objecting blocks the change on its own, and the system records exactly which one objected and why — a disqualifying classification can override a safe-looking score, and a borderline score can be cleared by a confident, safe classification.

The threshold itself is relative, not absolute. The cutoff is a percentile measured against the customer's own recent score history, so the same percentile setting resolves to a different number for a quiet repository than for one in the middle of an incident spree — on purpose, because "safe enough" means something different in those two situations.

Finally, the model watches its own track record. Every outcome reported from production — a revert, an incident, a confirmed-safe merge — nudges the model immediately by a small, careful amount. A slower, periodic batch refit retrains the whole model from its full history, and that retrained model is only promoted into production if it measurably performs at least as well as the one already live.

The feedback loop. A real-time nudge reacts the same day; a periodic batch refit corrects drift and must clear a promotion gate before going live.

The Evidence

A claim this specific deserves more than a demo. Forty-six hand-written scenarios run through the actual production decision path — every stage of the funnel, all ten finding categories, every mode shortcut, every threshold boundary — and none of them are reimplemented separately from the real code. If the real engine changes, these scenarios run against the change directly.

The threshold dial is measured, not asserted. A real experiment computes exactly what each percentile setting resolves to on a realistic mix of reviews, including both extremes stated precisely: the strictest possible setting approves nothing in the mix, and the most lenient possible setting approves everything except the single riskiest item — because nothing in a sorted list of scores can fall below its own maximum.

The learning loop is proven with real numbers, not described in the abstract. A held-out risky review's score moved from 0.668 to 0.975 to 0.999 as real outcomes were applied to the model in sequence, while a genuinely safer held-out review moved in the opposite direction over the same run — evidence of discrimination between the two, not simple upward drift.

A real limitation is named here on purpose, instead of left out. One feature's learned weight can under-update when the training data never varies it at all — found, measured, and written down rather than smoothed over, because an evidence section that only shows wins is not evidence.

Production trust does not stop at a test suite. A live Reports → Auto Approve dashboard shows an org's own score distribution plotted against its real cutoff, its real approve-and-block counts over time, its real override rate, and a real false-approve rate computed from outcomes reported on actual production traffic.

What This Is Worth to the Customer

Translate the mechanism into the customer's own units, and the trade becomes concrete. At a representative 500 pull requests a month, a 60% auto-approval rate, and a measured 1% false-approve rate, the arithmetic looks like this:

reviewer-hours returned  = 300 auto-approved PRs x 15 min saved / 60  = 75 hours/month
false approvals          = 300 auto-approved PRs x 1%                 = 3 reviews/month
expected incident cost   = 3 x (illustrative $2,000 cleanup cost)     = $6,000/month

Whether that trade is worth it depends entirely on what a team's own reviewer-hours and its own incident costs are worth — there is no universal answer — but the customer can now run this exact arithmetic with their own real numbers instead of guessing.

The percentile dial is the customer's lever, and for the first time it is visible. A more conservative setting costs more reviewer time and buys a lower false-approve rate. A more lenient setting trades the other way. Neither choice is hidden behind a black box; both are measured, per organization, continuously.

An override rate that climbs over time is an early warning the customer gets for free. It surfaces policy drift before an incident would have told the same story — often days or weeks earlier, while there is still time to adjust the dial rather than clean up afterward.

Nothing about this is a one-way door. always_approve and never_approve exist per repository for teams who already know their own risk profile. The static-rule check can never be silenced by a mode override — "we trust this repository" is never allowed to quietly become "ignore a leaked credential." And any single decision, in either direction, can be overridden by a human at any time, with that override logged and counted.

Risks and What We're Watching

A brand-new customer org has no score history to calibrate a percentile against on day one. The system falls back to an explicit, conservative fixed cutoff in that case, rather than silently assuming everything is safe until enough real history accumulates.

Thin training data can under-protect a feature, as the documented weight-collapse case shows. The batch-refit promotion gate — never promote a model that performs worse than the one already live — is the deliberate safeguard against that kind of drift reaching production unnoticed.

This system is one layer in a funnel, not the last line of defense. The static-rule check and the independent LLM classification exist specifically so that no single signal is ever the only thing standing between a risky change and production.

One capability was scoped and deliberately set aside for a later phase: a live, observe-only mode that would let a new customer watch the policy's decisions on real incoming traffic before trusting it to act. It is a known next step, named here rather than hidden, and the three measurement views described above were prioritized first because they work against decisions the system is already making today.

Appendix: Frequently Asked Questions

Customer questions

Does this mean less code review?

No. It means the review that happens is concentrated on changes that carry actual risk, instead of spread evenly across everything regardless of risk.

What happens on day one, with no history?

The policy falls back to an explicit, conservative, fixed cutoff until enough real reviews accumulate for a percentile to be calculated against the org's own data.

Can I turn this off for one repository but keep it on elsewhere?

Yes. Mode and threshold are both configurable per repository, and a repository without its own setting simply inherits the organization's default.

What stops the robot from approving something dangerous?

Three independent checks must all agree that nothing is wrong — eligibility, static rules, and the risk-score-plus-LLM pair — and any one of them can block the change by itself.

Internal and hard questions

How do we know the 46-scenario corpus isn't cherry-picked?

It deliberately includes adversarial cases built to fail a naive approach — for example, a high-blast-radius change with zero flagged findings, the exact pattern a severity-only check would miss entirely.

What is the actual false-approve rate today, and is it acceptable?

This is now a measured, per-org number on the Reports → Auto Approve dashboard, not an estimate — and it is the number that should gate any decision to widen the rollout.

Why logistic regression instead of a more powerful model?

Explainability is a requirement here, not a nice-to-have, because the model's output decides whether a human ever sees the code at all. RADAR made the same choice, for the same reason.

What is the plan if an org's override rate starts climbing?

Treat it as the earliest available signal that a threshold or a model weight has drifted out of step with that org's current reality, and investigate before an incident does the same job the hard way.
